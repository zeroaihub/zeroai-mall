# 下单提议「点了确认却没生成订单」修复说明

## 一、现象

H5 AI 导购里生成下单提议后点「确认下单」：

- 卡片显示「已提交，订单号 1794464786000006」，提示下单请求已提交；
- 但「我的订单」里查不到这张订单，数据库 `shop_order` 也没有对应记录。

## 二、根因（两层，缺一不可）

### 1. 直接原因：消息消费端没启动

下单链路是异步的：

```
确认接口 → IMobileOrderService.asyncSubmit（算价 + 生成订单号 + 写本地消息表）
        → relay 投递 RabbitMQ order_direct_queue
        → zeroai-message-consumer 消费 → 回调 mobile-api /callback/order/submit → 落库
```

现场证据：

- `order_direct_queue` 有 4 条 ready、**consumers = 0**，消息没人消费；
- 只有一个 java 进程（mobile-api，82），消息消费端（85）根本没跑；
- 把消费端启动起来后，这 4 条消息立刻被消费，其中 1 条落单成功（订单 19）。

### 2. 系统原因：确认接口把「消息已投递」当成「订单已创建」

`ActionProposalService.confirm()` 原来拿到 `asyncSubmit` 的返回值就直接
`markConfirmed()` 并返回 `ok=true`，没有校验消费端是否真的落库。
消费端停摆时，用户会拿到一个**查不到的订单号**，且提议被永久标记为 CONFIRMED，
重试也走不通（会返回「已确认过」）。

历史数据可以佐证：`ai_action_proposal` id=3（user 93）status=CONFIRMED、
order_sn=1793070666000005，但 `shop_order` 里从来没有这个订单号。

> 附带发现：这 3 条老消息真正失败的原因是
> `shop_order_goods.specifications doesn't have a default value`——
> 早期购物车行没有写 specifications，落单时批量插入为 NULL 被数据库拒绝。
> 新购物车行都有该字段，不是本次要修的主线，但历史脏数据重放时会复现。

## 三、修复

### 环境

1. 启动消息消费端（与 mobile-api、MySQL、Redis、RabbitMQ、ES 并列，属必需进程）：

```bash
java -jar jars/zeroai-message-consumer.jar --server.port=85
```

2. 启动 mobile-api 时必须**加载 `.env`**，否则
   `zeroai.ai.enabled` / `zeroai.ai.action.enabled` 都是 false，
   `/ai/action/**` 整个控制器不注册（表现为 404「No static resource ai/action/confirm/...」）：

```bash
set -a && . ./.env && set +a
java -jar jars/zeroai-mobile-api.jar --server.port=82
```

### 代码（让「没订单」不再被谎报成成功）

| 文件 | 改动 |
| --- | --- |
| `IMobileOrderService` / `MobileOrderServiceImpl` / `OrderQuerySupport` | 新增 `searchSubmitResult(orderSn)`：返回落单原始结果，**未出结果时返回 null**，与既有 `searchResult`（null 兜底成「下单失败」）区分开 |
| `ActionProposalProperties` | 新增 `result-wait-ms`(2000)、`result-poll-interval-ms`(100)、`confirm-timeout-seconds`(120) |
| `AiActionProposalMapper` | 新增 `bindOrderSn`：确认时先落订单号，等待超时后仍能回查 |
| `ActionProposalService.confirm` | 投递后先 bindOrderSn，再在等待窗口内轮询结果：`success` → CONFIRMED；明确失败 → REJECTED + 具体原因；无结果 → 返回 `processing=true` 保持 CONFIRMING |
| `ActionProposalService.get` | 查询时惰性回收 CONFIRMING：按 orderSn 回查结果缓存 → CONFIRMED / REJECTED；超过 `confirm-timeout-seconds` 仍无结果 → REJECTED(CONFIRM_TIMEOUT) |
| `ConfirmResVO` | 新增 `processing` 字段，三种形态：已落库 / 处理中 / 明确失败 |
| `ProposalRejectCode` | 新增 `CONFIRM_TIMEOUT`「订单创建超时，请到「我的订单」确认是否已生成」 |
| `revalidate` | 拒绝原因补 `detail` 明细（哪一行、快照值 vs 实时值），只进日志不返给用户 |
| H5 `ai/index.vue` + `api/ai.js` | `processing=true` 时卡片保持「提交中」，轮询 `GET /ai/action/{proposalNo}`（1.2s × 10 次）直到出结果 |

## 四、验证（本机实测）

| 场景 | 结果 |
| --- | --- |
| 消费端正常，确认提议 | `ok=true, processing=false`，耗时 1.1s，订单 20 落库，提议 CONFIRMED |
| **消费端停机**，确认提议 | `ok=true, processing=true`、「订单正在创建中」，耗时 2.2s，**不再谎报订单号** |
| 消费端停机时轮询提议 | `CONFIRMING`「确认正在处理中」 |
| 消费端恢复后轮询提议 | 自动回收为 `CONFIRMED`，订单 21 落库（orderSn 一致） |
| 单测 `ActionProposalServiceTest` | 29 个用例全绿（新增 5 个：处理中、消费端失败、查询回收、超时兜底、窗口内不误判） |

> 验证过程在库里留下了订单 19/20/21 与提议 id=5（商品名 TestPhone）等测试数据，可按需清理。

## 五、运维清单（避免再次踩坑）

1. **必需进程**：MySQL(3306)、Redis(6379)、RabbitMQ(5672)、ES(9200)、mobile-api(82)、
   message-consumer(85)、admin-api(81)。
2. 判断下单链路是否健康，先看队列：`order_direct_queue` 的 **consumers 必须 ≥ 1**，
   ready 持续堆积就说明消费端没起来。
3. mobile-api 打包前必须先停进程：`jars/zeroai-mobile-api.jar` 被占用时，
   spring-boot repackage 会报 `Unable to rename ... .jar.original`。
4. 本机 shell 里存在 `SERVER__PORT=42875` 环境变量，会覆盖 `application.yml` 的
   `server.port`；启动任何 Spring Boot 应用都要显式带 `--server.port=xxx`。
5. mobile-api 的 AI 能力全部靠 `.env` 注入，直接 `java -jar` 会得到一个「AI 全关」的实例。
