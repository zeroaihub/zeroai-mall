# AI 知识库 · 客服工单切片与检索方案

## 一、背景：工单 RAG 与政策 RAG 是两件事

现有 `zeroai-ai-starter` 的知识库（`com.zeroai.ai.knowledge`）解决的是**政策问答**：语料是 6 篇人工编写的 `kb-*.md`，结构规整、按小节组织、内容长期稳定、无隐私。

客服工单是另一类语料，四个差异决定了它不能直接套用现有链路：

| 维度 | 政策文档 | 客服工单 |
|---|---|---|
| 结构 | Markdown 标题 + 段落 | 结构化字段 + 多轮对话 |
| 语义单元 | 一个小节讲一条规则 | **一张工单讲一个完整案例** |
| 噪音 | 无 | 寒暄、重复追问、内部备注、脏话、模板话术 |
| 时效 | 版本化，人工维护 | 政策一变就大面积过期 |
| 隐私 | 无 | 手机号、地址、姓名、订单号 |
| 检索目标 | 「规则怎么说」 | 「别人遇到同样问题怎么解决的」 |

**核心判断：工单不需要找切片模型，需要「提纯 + 结构化」。** 一张工单本身就是语义完整的原子单元，按 `chunkSize=300` 去切，只会把「问题」和「解决方案」切到两个块里，两块都不可用。

## 二、总体思路：提纯前置，切片复用

不新增专用 chunker，先把工单**离线提纯成伪 Markdown**，再交给现有 `KnowledgeChunker.split()` 处理。理由：

- `KnowledgeChunker` 的「标题即语义边界」策略对工单同样成立——提纯后的小节就是「问题 / 场景 / 方案 / 边界」；
- `prefixTitle=true` 会自动给每块拼上 `【工单标题 · 小节】`，正好补上工单块缺失的主题上下文；
- 少一个类、少一套单测，符合本项目「最小可维护改动」的准则。

等 v1 跑通、评测集证明切片是瓶颈之后，再考虑 Late Chunking 或语义切片（见第七节）。

### 2.1 提纯模板（离线 LLM 任务，非在线链路）

对每张**已解决**工单调用小模型（Qwen3-14B / 豆包 lite 级别足够），输出固定四段：

```markdown
## 问题
用户当时怎么问的（保留用户原话关键词，口语化，不要改写成客服术语）

## 场景
订单状态 / 商品类目 / 支付方式 / 是否已发货（只保留与答案相关的）

## 处理方案
客服实际做过的动作，分条，可执行

## 边界
这个方案不适用的情况
```

三条硬约束：

1. **「问题」段必须用用户口吻**。这是 query–document 对齐的关键：在线 query 是「我退款怎么还没到账」，历史工单标题是「客户咨询退款进度异常」。如果提纯时也写成客服术语，两边措辞永远对不上，BM25 和向量都会掉分。
2. **禁止一次性动作**。「已为您加急处理」「已补偿 20 元」这类不可复用的内容要剔除，它们会诱导模型承诺无法兑现的动作。
3. **必须产出「边界」段**。否则模型会把特例当通例——工单里「这个用户因为是 VIP 所以特批」会被当成通用政策。

提纯结果写回 `KnowledgeDocument.content`，`tags` 由工单分类 + 商品类目生成。

### 2.2 入库前的分流规则

| 工单情况 | 处理方式 |
|---|---|
| 已解决 + 提纯后 ≤ 500 字 | 整单一块，不分片 |
| 已解决 + 提纯后 > 500 字 | 走 `KnowledgeChunker.split(chunkSize=500)`，按四个小节自然分块 |
| 未解决 / 无有效客服回复 | **不入库**。没有答案的案例只会污染召回 |
| 纯投诉、情绪宣泄 | 不入库。可单独进投诉分析索引，不参与对话检索 |
| 同一问题累计 ≥ N 张（建议 N=5） | **聚类合并成一条 FAQ**，人工审核后入库 |

最后一条是最容易漏的：真实工单库里同一个问题会有几十张重复单。全量直接入库，检索 Top-3 会全是同一个问题的不同措辞，等于只召回了一个案例。入库前去重比检索后做 MMR 更划算。

## 三、参数建议

在 `zeroai.ai.knowledge.*` 基础上，工单索引建议独立一套值：

| 配置 | 政策文档现值 | 工单建议值 | 依据 |
|---|---|---|---|
| `vector.chunk-size` | 300 | **500** | 工单要装下「问题+方案」，300 会切碎方案步骤 |
| `vector.min-chunk-chars` | 60 | **120** | 避免「边界」段单独成块后过于碎片化 |
| `vector.prefix-title` | true | **true** | 工单块尤其需要主题前缀，否则「3 个工作日」这种块脱离语境 |
| `max-hits` | 3 | **3**（不变） | 工单相似案例 3 条足够，多了是重复噪音 |
| `max-snippet-chars` | 600 | **800** | 工单块本身更长 |
| `min-score`（BM25） | 1.5 | **从 1.5 起测** | 工单口语化，词元分布不同，必须按新语料重测 |
| `vector.min-score` | 0.55 | **0.60 起测** | 工单表述更随意，0.55 容易放进同主题但不同问题的块 |
| `embedding.model` | text-embedding-v3 | **BAAI/bge-m3** | 中文短问句 + 长工单混排，bge-m3 的稠密/稀疏双输出更稳 |

阈值没有跨语料可迁移性，必须用评测集重标定——这一点现有 `KnowledgeProperties` 的注释已经写得很清楚，工单语料同样适用。

## 四、检索设计

在现有 `KnowledgeSearchRouter` 的 BM25 / vector / hybrid 三模式下，工单索引需要额外两件事：

### 4.1 字段加权（BM25 侧）

工单的「问题」字段权重必须高于「处理方案」：

```
title^2.0 / 问题段^2.0 / 处理方案^1.0 / 场景^0.5
```

否则「退款」这个词在方案段高频出现，会把一堆主题不相关的工单顶上来。

### 4.2 业务过滤（必须前置，不是后置）

- `resolved = true`：只检索已解决的
- `category` / `sku_category`：同品类优先。数码品类的退货工单对服饰品类基本无参考价值
- `policy_version`：政策变更后，旧工单要么重新提纯，要么降权

### 4.3 时效衰减

工单不设 `updatedAt` 硬过滤，改用软衰减：距离政策最近一次变更超过 180 天的工单，RRF 融合分乘 0.8。**不要把衰减做进向量相似度**，余弦分被污染后不可解释，放在融合层最干净。

## 五、与现有模块的接入点

| 能力 | 复用 / 新增 | 说明 |
|---|---|---|
| `KnowledgeChunker` | **复用** | 输入提纯后的伪 Markdown，无需改动 |
| `KnowledgeHit` / `KnowledgeDocument` | **复用** | 字段够用；`sourceId` 用 `ticket-{id}` 前缀区分 |
| `KnowledgeGuard` | **扩展** | 现有只有 Prompt Injection 防护，**必须新增 PII 脱敏**（见 5.1） |
| `KnowledgeProperties` | **需改** | 当前 `index` 是单值 `zeroai_ai_kb`，工单需要独立索引或改为按 category 路由 |
| `KnowledgeSearchRouter` | **需扩展** | 增加字段加权与 `policy_version` 过滤 |
| `Bm25KnowledgePort` / `VectorKnowledgePort` | **复用** | 换索引名即可 |

### 5.1 隐私脱敏（新增，不可省）

工单是真实用户数据，入库前必须按顺序处理：

1. 手机号 → `[手机号]`
2. 身份证 / 银行卡 → `[证件号]`
3. 收货地址 → `[地址]`（保留到市级，区县以下抹掉）
4. 姓名 → `[姓名]`
5. 订单号 / 支付流水号 → `[订单号]`
6. 内部备注、客服工号 → 整段剔除

脱敏放在提纯 LLM 之后、入库之前，作为**确定性代码**执行，不依赖 LLM 自觉。丢一张工单没关系，漏一个手机号进索引就是数据事故。

## 六、ES 索引 mapping（工单索引）

```json
{
  "mappings": {
    "properties": {
      "sourceId":     { "type": "keyword" },
      "ticketId":     { "type": "keyword" },
      "title":        { "type": "text", "analyzer": "ik_smart", "fields": { "raw": { "type": "keyword" } } },
      "titleWeighted":{ "type": "text", "analyzer": "ik_smart", "boost": 2.0 },
      "problem":      { "type": "text", "analyzer": "ik_smart", "boost": 2.0 },
      "solution":     { "type": "text", "analyzer": "ik_smart" },
      "scene":        { "type": "text", "analyzer": "ik_smart", "boost": 0.5 },
      "boundary":     { "type": "text", "analyzer": "ik_smart" },
      "chunkText":    { "type": "text", "analyzer": "ik_smart" },
      "vector": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine"
      },
      "category":      { "type": "keyword" },
      "skuCategory":   { "type": "keyword" },
      "resolved":      { "type": "boolean" },
      "policyVersion": { "type": "integer" },
      "section":       { "type": "keyword" },
      "updatedAt":     { "type": "date" },
      "visibility":    { "type": "keyword" }
    }
  }
}
```

`dims` 必须与 `zeroai.ai.knowledge.embedding.dimension` 一致——现有实现把维度当**校验值**而不是旋钮，配错不会报错，只会永远返回不相关结果。

## 七、切片模型的引入时机

不要一上来就上模型。按这个顺序验证：

1. **v1（推荐先做）**：提纯 + 现有 chunker，500 字整单/分节。覆盖 80% 场景，零新增模型。
2. **v2**：若评测显示「规则被切成两半导致答非所问」，再上**语义切片**（逐句 `bge-m3` 编码，相邻相似度跌幅超阈值处切）。索引成本约 3x。
3. **v3**：若长工单（多轮对话 > 2000 字）召回明显差，上 **Late Chunking**（`jina-embeddings-v3` 整篇编码后切 token 向量），让每块带全文语境。索引成本约 5x。
4. **不建议**：上下文切片（每块 LLM 补摘要，30x 索引成本）。工单量大、更新频繁，成本不划算；提纯阶段已经补过上下文了。

## 八、评测

沿用现有 29 条用例的评测思路，工单侧至少要有：

- **命中率**：30 条真实用户问法，人工标注正确工单，看 Top-3 命中率
- **口径**：按「问题+方案」是否可直接转述给用户判定，不看字面匹配
- **反例集**：10 条应当查不到的问题（如「能不能帮我改收货地址」），验证不会硬凑一张相似工单
- **阈值标定**：`min-score` 与 `vector.min-score` 用这 40 条重新扫描，不要继承政策的 1.5 / 0.55

反例集比正例集重要：工单检索最危险的失败不是查不到，而是查到一张看似相关但方案不适用的工单，模型照着答，用户按错的方法操作。

## 九、非目标

- 不做工单实时入库。提纯是离线批量任务，在线链路只读索引。
- 不做跨租户/跨商家的工单共享检索，可见范围沿用 `KnowledgeVisibility`。
- 不新建资金拆分或对账相关的工单统计表。
- 不在本次改动中调整政策文档（`kb-*.md`）的任何现有切片参数。
