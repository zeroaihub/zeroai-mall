# 商品索引自动同步修复

> 现象：运营后台新增「苹果手机」并上架，H5 与 AI 助手都搜不到。
> 结论：商品写路径从未同步 ES，属于历史遗留缺陷。本文记录根因、修复与验证。

## 一、根因

搜索链路是 **ES 召回 + MySQL 回填**，不是直接查库：

```
AI search_products / H5 搜索框
  → SearchApplicationService.searchResult()
  → ES 索引 goods（filter isOnSale=true，match name / pyname / keyword）
  → 按 ES 返回的 id 顺序回查 shop_goods 补展示字段
```

而商品写路径里只有「删除」碰了 ES：

| 操作 | 方法 | 是否同步 ES |
|---|---|---|
| 新增 | `GoodsMutationSupport.saveGoodsRelated` | ❌ 只写库 |
| 修改 / 上下架 | `GoodsMutationSupport.updateGoodsRelated` | ❌ 只写库 |
| 删除 | `GoodsMutationSupport.deleteGoodsRelatedByGoodsId` | ✅ 删文档 |

全项目只有两处写索引：`syncGoodsToEs()`（全量重建，后台按钮）与 `syncGoods2Es(goods)`，
后者**零调用方**——定义了但从未接线。所以新增/改价/上下架后索引永远停在旧状态，
极端情况下还会出现「库里已下架、搜索里仍能买到」。

排查时的关键证据：`GET /goods/_doc/1181013` 返回 `found:false`，而 `shop_goods` 里有该商品且 `is_on_sale=1`。

## 二、修复

### 1) 写路径接上索引同步（`GoodsMutationSupport`）

- 新增、修改：方法末尾调用 `syncGoodsIndexAfterCommit(goodsId)`。
- 删除：原先在事务内删 ES 文档，改为同样走提交后回调。
- 两处都通过 `runAfterCommit()` 统一处理：

```
有事务 → TransactionSynchronizationManager.registerSynchronization(afterCommit)
无事务 → 立即执行（便于单测直接调用）
```

三个刻意的设计选择：

1. **放在 afterCommit 而不是方法体里**：事务回滚时不能把未生效的数据写进索引；
   删除同理，否则回滚后会出现「库里有商品、索引里没有」的假丢失。
2. **提交后按 id 重新查库再同步**（`goodsMapper.selectById`），不用入参对象拼文档——
   入参缺虚拟销量、缺货品最低价，`goods_sn` 也是插入后才回填的。
   若查不到（并发删除），转而删索引，不留残影。
3. **同步失败只记 WARN 日志**，不向上抛。索引是派生数据，不能反过来让商品保存失败；
   代价是可能出现「保存成功但搜不到」，所以日志里明确写了「商品已保存但搜索结果可能不同步」。

### 2) 后台「同步es」按钮的两个问题

- 前端 `v-hasPermi` 写的是 `system:goods:*`，后端 `@PreAuthorize` 是 `shop:goods:*`，
  整页四个按钮的权限串都和 `sys_menu` 对不上。已统一为 `shop:goods:*`。
- `sys_menu` 里没有 `shop:goods:syncEs` 记录，非超管角色无法授权 → 按钮永远不显示。
  已补一条 F 类型菜单（parent_id=2037 商品管理，menu_id=2127）。
- 注意超管（role_key=admin）走 `*:*:*`，所以此前按钮对 admin 可见、对普通角色不可见，问题被掩盖了。

### 3) 顺带修掉 `ElasticDocument.insertOrUpdateOne` 的返回值误判

第一次接上同步后，新增商品的日志里立刻出现了一条 WARN：

```
WARN GoodsMutationSupport - 商品索引同步失败，商品已保存但搜索结果可能不同步, goodsId=1181014
BusinessException(msg=商品同步 ES 失败) at GoodsElasticSyncSupport.syncGoods2Es:80
```

但去 ES 查，文档**明明已经写进去了**。原因是：

```java
// 修复前
return indexResponse.status().equals(RestStatus.OK);
```

ES 对「新建文档」返回 **201 CREATED**，对「覆盖更新」返回 **200 OK**。
只判 200 会把所有新增判成失败——文档写成功却抛异常。

这解释了为什么 `syncGoods2Es` 长期没人调用还能「看起来没问题」：它一旦用于新增就会抛错。
修复为两者都算成功：

```java
RestStatus status = indexResponse.status();
return status == RestStatus.OK || status == RestStatus.CREATED;
```

修复后复验新增（商品 1181015）：无任何 WARN，库与索引同时出现该商品。

## 三、验证（真实链路，非单测）

后台登录 → 调真实接口 → 查 ES，全流程无手工干预：

| 步骤 | 操作 | 结果 |
|---|---|---|
| 新增 | `POST /shop/goods`（ES同步验证机，199 元，已上架） | 库 id=1181014；**ES 文档自动出现**，字段齐全（name/retailPrice/keyword/isOnSale…） |
| 可搜 | `GET /search/result?keyword=同步验证机` | 首条命中 |
| 修改 | `PUT /shop/goods` 改价 188、改名 | ES 中 `name` 与 `retailPrice` 同步变为新值 |
| 删除 | `DELETE /shop/goods/1181014` | ES 文档 `found:false`，MySQL 为逻辑删除（del_flag=1） |
| 复验新增 | `POST /shop/goods`（ES同步复验机，99 元） | 修复 CREATED 判定后**无 WARN**，库与 ES 同时出现 |
| 存量 | 对比总数 | MySQL 有效商品 231 = ES 文档 231，无其它缺口 |

验证结束后两个测试商品均已删除，库与索引数量回到 231 = 231。

单测：`zeroai-domain-goods` 21 个全绿，其中 `GoodsMutationSupportTest` 新增 4 条
（新增触发同步 / 使用库里最新数据 / 同步失败不影响保存 / 删除移除索引）。

## 四、边界与遗留

- **虚拟销量不触发同步**：`updateVirtualSales` 每笔订单都调用，逐单写 ES 不值当。
  ES 里的 `sales` 因此可能落后，只影响「按销量排序」的精度，不影响能否搜到。
  如需精确，应改为定时批量回写。
- **全量重建仍是删索引再重建**（`deleteIndex` → `createIndex` → 批量写），
  重建窗口内搜索为空。商品量大时建议改成双索引别名切换。
- **逻辑删除**：删除商品后 `shop_goods` 行仍在（del_flag=1），排查时别误判成「没删掉」。
- 本次修复只覆盖后台管理端写路径；若后续有其他入口（导入、脚本直改库）改商品，
  仍需走 `IGoodsService.saveGoodsRelated/updateGoodsRelated`，否则索引会再次落后。
